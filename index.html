The User

Why?

Our game was created to provide an alternative resource for learning Data Structures and Algorithms. Because this topic is so technical, other resources tend to be dry and boring. By breaking problems down into small fun exercises, we hope to provide relief from the burnout traditional resources can bring.

Who?

As a student, you play Chronicles of Big O to learn about Data Structures and Algorithms through intuitive visuals and fun gameplay.

As a job seeker, you play Chronicles of Big O to review Data Structures and Algorithms related to Leetcode to prepare you for technical interviews in a fun manner that can help prevent burnout.

As a teacher, you supplement your lessons with Chronicles of Big O to help reinforce your student's knowledge of Data Structures and Algorithms.

What?

In our game, we represent each data structure with an object that has similar properties and center the exercises around the object in a way that makes sense. For example, we convert an array data structure into a train with windows, where each window represents the array's indices. This helps with visualizing the data structure and the problem, allowing for a more engaging and immersive experience. Additionally, it teaches the players in an educational environment that allows them to make mistakes and learn from them.

How?

Array Level:

  • Phase 1: Insertion into an array to teach O(1) insertion
  • Phase 2: Linear searching of an array in O(N) time
  • Phase 3: Bubble sort to teach sorting in O(N²) time
  • Phase 4: Binary search to teach O(logN) search element search time

Linked List Level:

  • Phase 1: Teaches them about nodes — specifically Head, Tail, and Links between them
  • Phase 2: Traversal of Nodes in a Linked List
  • Phase 3: Reversing a Linked List

Menu Design

The menu for the Array Level is split into 4 buttons, each representing a phase. I chose to have individual buttons for each phase of the game to aid the development process. Splitting each phase into its respective button, it allowed me as a developer to create a scene paired to the button. This made it so I could develop each phase incrementally instead of making each one depend on the other. Scenes are the core building blocks of the game and allow assets to be bundled in a scene without external impact. By creating the scenes one at a time, I was able to create the supporting back-end code for the phase without having to create code for any other phase despite them being conceptually connected.

UI

At first, we wanted the user to interact directly with the object. In the case of our Array level, we wanted passengers to be moved in the train. We had to eventually scrap this idea as we decided levels would take too long and wouldn't accurately reflect the operation times for arrays, especially if we had really large sizes like 15+.

Because of this issue, we designed a smaller array that would sit at the bottom of the user's screen. This made interacting with the array much simpler and similar to how a real array would work. Based on feedback and multiple iterations, we eventually landed on the current UI, with minimal changes to fit the correct phase.

Overall Capstone

Approach and Evolution

Initially, we had wanted to cover the fundamental concepts and move incrementally. As we started developing our project, we realized that we wanted to cover more complex data structures, as those were the highly technical concepts that most students struggled with. Later down the line, we also shifted our stance on letting users make mistakes, giving more freedom to the user to allow for greater learning opportunities.

Team Structure and Responsibilities

Dividing responsibilities among the two team members was a key part in ensuring we delivered a successful project by the set deadline. As a group, we assessed each group member's strengths and weaknesses and assigned responsibilities based on individual traits.

Lucas was primarily responsible for creating the supporting backend code to allow the sprites of the game to interact amongst each other. This included programming data structures to act as the underlying support for the visual data structures. Furthermore, this required programming assets to act as values inside the train as well as nodes in the linked list. These assets needed to be movable and updatable based on user input.

Daniel was responsible for creating visual assets and the front-end. This included creating the map, which was done layer by layer to allow edits throughout the development of the game. After the map creation, the UI was then created to support the backend code. This UI included indices for the array along with a drag and drop feature with connected support to the map. When a user dragged an NPC into the UI, it populates the train with that NPC and assigns it a respective index in the backend.

Challenges Faced and Lessons Learned

Through our capstone journey, we faced and overcame many challenges. One of the main challenges stemmed from working on such a big project over an extended period of time with a team. This is because we each worked on separate parts of the project. Later on, we realized that merging our work was actually really difficult because we hadn't planned a lot of our shared components. This meant that sometimes we'd have to completely modify one person's work to fit the others.

From this experience, we both learned how important planning is when dividing up work. Communicating and defining what individual work should look like will help save time and make merging work significantly easier and more efficient later down the road.

Something that was also useful for capstone was documenting our work as we were doing it. This helped with weekly reports as we didn't waste time trying to remember what we did or where our work was stored. It also made our reflections more accurate and detailed, as it was still fresh in our minds.

Conclusion

In conclusion, our group developed many new technical and emotional skills and delivered a strong demonstration of our original project concept. The current state of our project serves as an example of what the fully implemented game could become in the future. As a group, we contributed a combined 800 hours of work to both develop the game and complete all capstone assignments simultaneously. We spent many hours collaborating and dividing responsibilities among ourselves to ensure our weekly tasks were completed. Throughout the process, we improved our ability to communicate technical concepts clearly and maintained full transparency so that every member understood the true scope of the remaining work.

As we worked through the game, we encountered many technical challenges that required constant improvement from our group members to address. Many bugs and features required referencing documentation and tutorials to implement and fix. This experience taught us as developers to plan more effectively and to combat issues as they arise. Ultimately, our efforts created a game in which players can interact with complex data structures and algorithms in an intuitive way.

Next Steps

Moving forward, we plan to develop additional levels and expand on existing ones. Future level plans include Binary Trees, Queues, and Stacks. Additionally, game expansions will be made to reward the player for each level and phase completed. Each level will have a dynamic feature to allow for engaging and rewarding replayability. Ultimately, we hope to publish the game on Steam once these game additions are implemented.
