The User

Why?

Have you ever encountered a programming concept difficult to grasp? Are lectures, YouTube videos, or textbooks too technical and dry for you? Our game was created to provide individuals like you an alternative resource for learning Data Structures and Algorithms. By breaking problems down into small gamified exercises, we hope to provide you relief from technical and confusing traditional resources and the burnout using such resources can bring.

Who?

As a student, you play Chronicles of Big O to learn about Data Structures and Algorithms through intuitive visuals and fun gameplay.

As a job seeker, you play Chronicles of Big O to review Data Structures and Algorithms related to Leetcode to prepare you for technical interviews in a fun manner that can help prevent burnout.

As a teacher, you supplement your lessons with Chronicles of Big O to help reinforce your student's knowledge of Data Structures and Algorithms.

What?

Our game represents data structures with an object that has similar properties, and it centers the exercises around the object to make them easier for you to understand. For example, we convert an array data structure into a train with windows, where each window represents the array's indices. This helps you visualize the data structure and the problem, allowing for a more engaging and immersive experience. Additionally, it teaches you in an educational environment that allows you to make mistakes and learn from them.

How?

Array Level:

  • Phase 1: Insertion into an array to teach O(1) insertion
    • Instructions: Drag and drop train passengers into UI based on index.
  • Phase 2: Linear searching of an array in O(N) time
    • Instructions: Type an index to find the target value.
  • Phase 3: Bubble sort to teach sorting in O(N²) time
    • Instructions: Swap elements if the left is greater than the right.
  • Phase 4: Binary search to teach O(logN) search element search time
    • Instructions: Go left if mid is bigger than target, go right if mid is smaller.

Menu Design

Originally, the array level began in a single game scene that made assets appear and disappear. This implementation was extremely difficult to expand as a developer due to the high connectivity between assets. I then opted to fix this problem by creating a menu with separate scenes. The menu for the Array Level is split into 4 buttons, each representing a phase. Splitting each phase into its respective button allowed me as a developer to create a scene paired to the button. This made it so I could develop each phase incrementally instead of making each one depend on the other. Scenes are the core building blocks of the game and allow assets to be bundled in a scene without external impact. By creating the scenes one at a time, I was able to create the supporting back-end code for the phase without having to create code for any other phase, despite them being conceptually connected. I then added a developer button to allow myself to reset a hypothetical user's progress. Once the level was complete, I created the final menu without the developer button and polished it to fit the theme of the game.

Array Level Design

Phase 1 — Insertion

Phase 1 began with drafting the initial idea of how we wanted to teach the user how to use array indices and insert elements in O(1) time. My initial backend design allowed the user to drag an element labeled with an index into 5 different index slots. If they dragged it to the correct index, it flashed green, and if they dragged it to the wrong index, it flashed red. Though this design allowed insertion, we felt it did not allow the user to fail and learn from their mistakes. I then redesigned the phase to allow the user to drag and drop passengers into any index. This change, paired with a submit button, allowed the user to make mistakes without immediate feedback and correction. This way of designing the level allows the user to understand they made a mistake without directly telling them where they went wrong, ultimately aiding their learning.

Phase 2 — Linear Search

We designed phase 2 to allow the user to get an intuitive feel of linear searching an array for a random element in O(N) time. My initial design involved allowing the user to press a start button with the target index and click crates one at a time to reveal the value at that index. This design worked well, but we felt the user lacked an understanding of indices with this approach. I then redesigned phase 2 to be interacted with through typing indices rather than clicking on random boxes. This allowed the user to directly see the impact of an index and what going out of bounds resulted in. The backend supports out-of-bounds errors by giving the user visual feedback, and the user completes the level when the value at the index they type matches the target value.

Phase 3 — Bubble Sort

Our initial phase 3 was designed with a searching algorithm in mind to show the user how to make an unsorted array sorted, and then allowing them to search it after. We decided to implement bubble sort because we felt it was the easiest to visually demonstrate and interact with while also showing its inefficiency when it comes to comparable sorting algorithms. My initial design consisted of two different functionalities: the user could click the highlighted values to swap them or click a button to not swap. If the user got the swap or didn't swap decision right or wrong, they were instantly shown the correct answer. We then felt that this immediate feedback allowed the user to brute force the swaps and lacked an educational element. I then redesigned the level to separate the swap and don't swap into respective buttons. Finally, I chose to verify correctness at the end of each pass. This allows the user to freely make mistakes up until the end of a single pass of the array. The backend implementation of this allows the user to make mistakes and focus on making the correct swap/don't swap decisions without brute force.

Phase 4 — Binary Search

Our goal for phase 4 was to allow the user to use their now sorted array to find an element in O(logN) time. I chose to implement the sorted array from phase 3 to allow the user to use the exact same array with the same values. This implementation allowed the user to see the results of their work from phase 3 without generating new sorted arrays. In our initial design for binary search, we allowed the user to choose left, right, or found. This implementation gave immediate right or wrong feedback, which once again let the user brute force the correct solution. In our final iteration, I implemented a second part for the binary search. This second part requires the user to type the indices based on their decision of left and right. This implementation allows the user to consider the core functionality of the binary search algorithm while allowing them to learn from their mistakes.

Visual Assets

When developing the assets like the map or character nodes, I first created very basic versions and added to them as required. UI

At first, we wanted the user to interact directly with the object. In the case of our Array level, we wanted passengers to be moved in the train. We had to eventually scrap this idea as we decided levels would take too long and wouldn't accurately reflect the operation times for arrays, especially if we had really large sizes like 15+.

Because of this issue, we designed a smaller array that sits at the bottom of the user's screen. This made interacting with the array much simpler and similar to how a real array would work. Some additional features for our UI include highlighting hovered arrays, tooltips that display indices and passenger ticket numbers, and duplication of passengers in our train asset. Additionally, to make gameplay intuitive, each level has clear ways of interaction with assets. Based on feedback and multiple iterations, we eventually landed on the current UI, with minimal changes to fit the correct phase.

Most of the minimal changes were moving around buttons, or adding certain control nodes that can take user input to better match the design. For arrays, we have 4 phases mapped out. The first phase teaches users about indices because that's how you access elements inside. Since the user drags the passengers into the UI, phase 1 contains a submit button.

Phase 1

Phase 2 focuses on helping teach the user how to traverse and access elements in the array using what they learned in phase 1. In this phase, we prompt the user to type an index to search to find a specific target. We reveal the ticket number at the index typed and flash yellow if the wrong number is found and green if the correct one is found.

Phase 2

After learning how to traverse an array and getting comfortable with accessing elements using index numbers, we wanted users to learn how to sort. We ended up choosing bubble sort as our sorting algorithm as it would be easy to grasp for new players. For this phase, the two indices set to swap are highlighted yellow. At the end of one pass, if you swap everything correctly, the passenger is highlighted green. If you make 1 or more incorrect swaps, the array will flash red and go back to its initial state before the current pass's swaps, allowing you to try again until you've sorted the entire array.

Phase 3

After sorting the array, we contrast random searching on an unsorted array with the more efficient searching algorithm, binary search, on a sorted array. The UI for this phase highlights the left, mid, and right indices to make it easier for the user to complete the level. This level is split into two different difficulties. For the first difficulty, you just go left and right based on the target and number at mid. You learn about the low and high indices through the highlighted passengers.

Phase 4 Easy

After 3 passes, we increase the difficulty and require the user to input the new low and high indices for the next search. To make things easier for the user, we still highlight low and high, and we show how the mid is calculated at the top.

Overall Capstone

Approach and Evolution

Initially, we had wanted to cover the fundamental concepts and move incrementally. As we started developing our project, we realized that we wanted to cover more complex data structures, as those were the highly technical concepts that most students struggled with. Later down the line, we also shifted our stance on letting users make mistakes, giving more freedom to the user to allow for greater learning opportunities.

Team Structure and Responsibilities

Dividing responsibilities among the two team members was a key part in ensuring we delivered a successful project by the set deadline. As a group, we assessed each group member's strengths and weaknesses and assigned responsibilities based on individual traits.

Lucas was primarily responsible for creating the supporting backend code to allow the sprites of the game to interact amongst each other. This included programming data structures to act as the underlying support for the visual data structures. Furthermore, this required programming assets to act as values inside the train as well as nodes in the linked list. These assets needed to be movable and updatable based on user input.

Daniel was responsible for creating visual assets and the front-end. This included creating the map, which was done layer by layer to allow edits throughout the development of the game. After the map creation, the UI was then created to support the backend code. This UI included indices for the array along with a drag and drop feature with connected support to the map. When a user dragged an NPC into the UI, it populates the train with that NPC and assigns it a respective index in the backend.

Challenges Faced and Lessons Learned

Through our capstone journey, we faced and overcame many challenges. One of the main challenges stemmed from working on such a big project over an extended period of time with a team. This is because we each worked on separate parts of the project. Later on, we realized that merging our work was actually really difficult because we hadn't planned a lot of our shared components. This meant that sometimes we'd have to completely modify one person's work to fit the others.

From this experience, we both learned how important planning is when dividing up work. Communicating and defining what individual work should look like will help save time and make merging work significantly easier and more efficient later down the road.

Something that was also useful for capstone was documenting our work as we were doing it. This helped with weekly reports as we didn't waste time trying to remember what we did or where our work was stored. It also made our reflections more accurate and detailed, as it was still fresh in our minds.

Conclusion

In conclusion, our group developed many new technical and emotional skills and delivered a strong demonstration of our original project concept. The current state of our project serves as an example of what the fully implemented game could become in the future. As a group, we contributed a combined 800 hours of work to both develop the game and complete all capstone assignments simultaneously. We spent many hours collaborating and dividing responsibilities among ourselves to ensure our weekly tasks were completed. Throughout the process, we improved our ability to communicate technical concepts clearly and maintained full transparency so that every member understood the true scope of the remaining work.

As we worked through the game, we encountered many technical challenges that required constant improvement from our group members to address. Many bugs and features required referencing documentation and tutorials to implement and fix. This experience taught us as developers to plan more effectively and to combat issues as they arise. Ultimately, our efforts created a game in which players can interact with complex data structures and algorithms in an intuitive way.

Next Steps

Moving forward, we plan to develop additional levels and expand on existing ones. Future level plans include Binary Trees, Queues, and Stacks. Additionally, game expansions will be made to reward the player for each level and phase completed. Each level will have a dynamic feature to allow for engaging and rewarding replayability.
