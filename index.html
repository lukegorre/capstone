The User

Why?

Have you ever encountered a programming concept difficult to grasp? Are lectures, YouTube videos, or textbooks too technical and dry for you? Our game was created to provide individuals like you an alternative resource for learning Data Structures and Algorithms. By breaking problems down into small gamified exercises, we hope to provide you relief from technical and confusing traditional resources and the burnout using such resources can bring.

Who?

As a student, you play Chronicles of Big O to learn about Data Structures and Algorithms through intuitive visuals and fun gameplay.

As a job seeker, you play Chronicles of Big O to review Data Structures and Algorithms related to Leetcode to prepare you for technical interviews in a fun manner that can help prevent burnout.

As a teacher, you supplement your lessons with Chronicles of Big O to help reinforce your student's knowledge of Data Structures and Algorithms.

What?

Our game represents data structures with an object that has similar properties, and it centers the exercises around the object to make them easier for you to understand. For example, we convert an array data structure into a train with windows, where each window represents the array's indices. This helps you visualize the data structure and the problem, allowing for a more engaging and immersive experience. Additionally, it teaches you in an educational environment that allows you to make mistakes and learn from them.

How?

Array Level:

  • Phase 1: Insertion into an array to teach O(1) insertion
    • Instructions: Drag and drop train passengers into UI based on index.
  • Phase 2: Linear searching of an array in O(N) time
    • Instructions: Type an index to find the target value.
  • Phase 3: Bubble sort to teach sorting in O(N²) time
    • Instructions: Swap elements if the left is greater than the right.
  • Phase 4: Binary search to teach O(logN) search element search time
    • Instructions: Go left if mid is bigger than target, go right if mid is smaller.

Menu Design

Originally, the array level began in a single game scene that made assets appear and disappear. This implementation was extremely difficult to expand as a developer due to the high connectivity between assets. I then opted to fix this problem by creating a menu with separate scenes. The menu for the Array Level is split into 4 buttons, each representing a phase. Splitting each phase into its respective button allowed me as a developer to create a scene paired to the button. This made it so I could develop each phase incrementally instead of making each one depend on the other. Scenes are the core building blocks of the game and allow assets to be bundled in a scene without external impact. By creating the scenes one at a time, I was able to create the supporting back-end code for the phase without having to create code for any other phase, despite them being conceptually connected. I then added a developer button to allow myself to reset a hypothetical user's progress. Once the level was complete, I created the final menu without the developer button and polished it to fit the theme of the game.

Array Level Design

Phase 1 — Insertion

Phase 1 began with drafting the initial idea of how we wanted to teach the user how to use array indices and insert elements in O(1) time. My initial backend design allowed the user to drag an element labeled with an index into 5 different index slots. If they dragged it to the correct index, it flashed green, and if they dragged it to the wrong index, it flashed red. Though this design allowed insertion, we felt it did not allow the user to fail and learn from their mistakes. I then redesigned the phase to allow the user to drag and drop passengers into any index. This change, paired with a submit button, allowed the user to make mistakes without immediate feedback and correction. This way of designing the level allows the user to understand they made a mistake without directly telling them where they went wrong, ultimately aiding their learning.

Initial Phase 1 Design

Final Phase 1 Design

Phase 2 — Linear Search

We designed phase 2 to allow the user to get an intuitive feel of linear searching an array for a random element in O(N) time. My initial design involved allowing the user to press a start button with the target index and click crates one at a time to reveal the value at that index. This design worked well, but we felt the user lacked an understanding of indices with this approach. I then redesigned phase 2 to be interacted with through typing indices rather than clicking on random boxes. This allowed the user to directly see the impact of an index and what going out of bounds resulted in. The backend supports out-of-bounds errors by giving the user visual feedback, and the user completes the level when the value at the index they type matches the target value.

Final Phase 2 Design

Phase 3 — Bubble Sort

Our initial phase 3 was designed with a searching algorithm in mind to show the user how to make an unsorted array sorted, and then allowing them to search it after. We decided to implement bubble sort because we felt it was the easiest to visually demonstrate and interact with while also showing its inefficiency when it comes to comparable sorting algorithms. My initial design consisted of two different functionalities: the user could click the highlighted values to swap them or click a button to not swap. If the user got the swap or didn't swap decision right or wrong, they were instantly shown the correct answer. We then felt that this immediate feedback allowed the user to brute force the swaps and lacked an educational element. I then redesigned the level to separate the swap and don't swap into respective buttons. Finally, I chose to verify correctness at the end of each pass. This allows the user to freely make mistakes up until the end of a single pass of the array. The backend implementation of this allows the user to make mistakes and focus on making the correct swap/don't swap decisions without brute force.

Initial Phase 3 Design

Final Phase 3 Design

Phase 4 — Binary Search

Our goal for phase 4 was to allow the user to use their now sorted array to find an element in O(logN) time. I chose to implement the sorted array from phase 3 to allow the user to use the exact same array with the same values. This implementation allowed the user to see the results of their work from phase 3 without generating new sorted arrays. In our initial design for binary search, we allowed the user to choose left, right, or found. This implementation gave immediate right or wrong feedback, which once again let the user brute force the correct solution. In our final iteration, I implemented a second part for the binary search. This second part requires the user to type the indices based on their decision of left and right. This implementation allows the user to consider the core functionality of the binary search algorithm while allowing them to learn from their mistakes.

UI

At first, we wanted the user to interact directly with the object. In the case of our Array level, we wanted passengers to be moved in the train. We had to eventually scrap this idea as we decided levels would take too long and wouldn't accurately reflect the operation times for arrays, especially if we had really large sizes like 15+.

Because of this issue, we designed a smaller array that sits at the bottom of the user's screen. This made interacting with the array much simpler and similar to how a real array would work. Some additional features for our UI include highlighting hovered arrays, tooltips that display indices and passenger ticket numbers, and duplication of passengers in our train asset. Additionally, to make gameplay intuitive, each level has clear ways of interaction with assets. Based on feedback and multiple iterations, we eventually landed on the current UI, with minimal changes to fit the correct phase.

Most of the minimal changes were moving around buttons, or adding certain control nodes that can take user input to better match the design. For arrays, we have 4 phases mapped out. The first phase teaches users about indices because that's how you access elements inside. Since the user drags the passengers into the UI, phase 1 contains a submit button.

Phase 1

Phase 2 focuses on helping teach the user how to traverse and access elements in the array using what they learned in phase 1. In this phase, we prompt the user to type an index to search to find a specific target. We reveal the ticket number at the index typed and flash yellow if the wrong number is found and green if the correct one is found.

Phase 2

After learning how to traverse an array and getting comfortable with accessing elements using index numbers, we wanted users to learn how to sort. We ended up choosing bubble sort as our sorting algorithm as it would be easy to grasp for new players. For this phase, the two indices set to swap are highlighted yellow. At the end of one pass, if you swap everything correctly, the passenger is highlighted green. If you make 1 or more incorrect swaps, the array will flash red and go back to its initial state before the current pass's swaps, allowing you to try again until you've sorted the entire array.

Phase 3

After sorting the array, we contrast random searching on an unsorted array with the more efficient searching algorithm, binary search, on a sorted array. The UI for this phase highlights the left, mid, and right indices to make it easier for the user to complete the level. This level is split into two different difficulties. For the first difficulty, you just go left and right based on the target and number at mid. You learn about the low and high indices through the highlighted passengers.

Phase 4 Easy

After 3 passes, we increase the difficulty and require the user to input the new low and high indices for the next search. To make things easier for the user, we still highlight low and high, and we show how the mid is calculated at the top.

Lucas Narrative

Approach and Evolution

In our senior year, Daniel and I were holding each other accountable to do one LeetCode problem each and every day, with a punishment if one of us fell short. Day to day, we developed our programming skills and felt better about LeetCode-style questions as we progressed. In our free time, we would both play games with each other and individually. We had previously worked together in coursework, often taking many of the same classes, and with our Capstone class around the corner, we started brainstorming.

The combination of working well together, our love for games, and our dedication to improving our computer science skills led us to create the idea for Chronicles of Big O. We combined these interests with the goal of making LeetCode fun, instead of feeling like a mindless grind. The first idea I had for the game was a 3D implementation using Unity. We soon found there was a lack of assets for 3D sprites and felt our time would be better spent making the game in 2D.

Once we decided to make a 2-Dimensional game, our game went through many iterations. Our initial idea involved a map in which the user could physically move their character to go from area to area to both learn new concepts and expand the world they occupied. We quickly found this scope was too large for the sake of the Capstone and decided on scoping the Capstone down to the level you see now, which consists of four unique phases in which you manipulate an Array. We felt the array is a fundamental computer science building block that will help them learn more difficult concepts later.

Team Structure and Responsibilities

Dividing responsibilities among the two team members was a key part in ensuring we delivered a successful project by the set deadline. As a group, we assessed each group member's strengths and weaknesses and assigned responsibilities based on individual traits.

I was primarily responsible for creating the supporting backend code to allow the sprites of the game to interact with each other. This included programming data structures to act as the underlying support for the visual data structures. Furthermore, this required programming assets to act as values inside the train as well as nodes in the linked list. These assets needed to be movable and updatable based on user input.

Additionally, I was responsible for creating the menu, to allow my development of the backend to be isolated for each phase. This separation of scenes allowed both Daniel and I to work on one phase at a time without needing any coupling between the phases. The menu greatly aided our development, and we soon saw large amounts of improvement in each iteration.

Challenges Faced and Lessons Learned

When developing the supporting code for the project, Daniel and I found it difficult to combine our work due to our separate programming implementations. We first scoped the array-level core functionality and decided what we wanted it to look like both in code and visually. I was tasked with creating the backend, and when it came time to combine our code, I quickly found I was missing assets Daniel had used, and my code methods took very different parameters while relying on different nodes. I struggled to refactor this code and learned how important it is to define code parameters and node structure before starting implementation. Looking back, Daniel and I should have communicated and planned this to allow smooth integration of our parts.

The second major challenge we faced in our group work was planning thorough schedules and meeting personal deadlines. Many times, Daniel and I would text each other in the morning to ask if we were available for that day. We would then meet that day and begin working on the assignments due for the week. At first, this worked for us, but we soon found that we were running out of time when we were meeting and would often have to meet the next day at inconvenient times to complete the work. I personally learned from this experience that communicating my availability along with my general mood and energy level can greatly improve my team's performance. Being honest with each other and time blocking made us a much more effective team, and we soon completed assignments before the deadline instead of at the last minute.

Conclusion

This capstone experience required me to invest 400 hours into developing a project, and I can confidently say that I am fulfilled with the resulting game. Daniel and I developed a strong first level that we can now expand greatly on. We no longer face the steep learning curve of game development and world-building, and are free to add as many DSA levels as we can take pride in. Through this project, I learned technical and communication skills and had the opportunity to build a working product from scratch. The entire development process was an integral part of furthering my education, and I look forward to future adventures.

Moving forward, I hope to make the levels more educational while the user is playing them without guiding them through text boxes. As the backend developer, I would like the user to gain a strong understanding of the data structures and algorithms without needing to give them written instructions. For example, the addition of making the user type the new indices for binary once they choose left or right allows the user to learn while playing the game. Though I achieved this in phase 4 of level one, I would like to make each level a seamless learning experience for the user. These levels will allow the user to have fun while truly learning in an intuitive way. Once we feel we have achieved these goals, we will move to publish it on Steam and give access to educators as a learning aid.

Daniel Narrative

Approach and Evolution

Initially, Luke and I came up with our project idea from grinding Leetcode. We both started off by using Neetcode as our learning resource. While Neetcode is an amazing resource, it falls short in certain areas. For example, he provides intuitive high level explanations of the concepts required to solve each problem, but doesn't go too deep into the low level ideas before showing the solutions. From this, we thought creating a resource that visualizes these problems could help individuals gain a better understanding of these concepts without showing the full solution.

From this idea, we ended up moving more towards data structures and algorithms as a more general resource to cater to a larger audience. We wanted to cover the fundamental data structures that students initially learn, and landed on Arrays, Queues, and Stacks. Later on, we thought that was too simple, and wanted to add more complex data structures. Because we underestimated the scope of our project, we ended up just creating a game around arrays.

Team Structure and Responsibilities

Luke and I hadn't really decided on individual roles and responsibilities until we got deeper into the first quarter. We hadn't really gotten a clear idea of what we wanted our project to look like, and spent a lot of time deciding what data structures we wanted to display in our project. When we started implementing our game, I ended up naturally shifting towards UI, while Luke worked more on the backend. These roles solidified more as the second quarter started.

Dividing responsibilities helped separate labor into two distinct categories, Frontend and Backend. This allowed Luke and I to work more efficiently in our own time and meet project deadlines. Luke mainly worked on creating the code to support the game mechanics. This included programming the logic behind each separate level and combining the scripts to work with the frontend nodes.

I was more responsible for creating the maps, visual assets, sprites, and the UI. The map was created using different layers to visualize the ground, key assets, and any decorations to make the scene look nicer. After the map was created, I made the passenger sprites, player sprites and animations, as well as the UI which is the main form of interaction between the user and the game.

Challenges Faced and Lessons Learned

Throughout our capstone journey, Luke and I faced and overcame many challenges. One of the main challenges we faced together was working on such a big project over an extended period of time. Through this time period, we had to coordinate our time through different school and work schedules and ensure proper communication about work done for the project. It was through this experience that I had learned how difficult it was to merge individual code into a polished final product.

A challenge I personally faced when working on creating the UI was creating something completely different from all the available tutorials online. I had envisioned creating the UI working a very specific way and found that all tutorials landed a bit short of what I wanted. I ended up having to watch multiple tutorials to emulate a final product I was happy with. From this I learned that most things you want to create aren't going to have exact blueprints and tutorials for you to follow. Most times you'll be learning small things and creating something big out of the bits and pieces you pick up along the way, which I've come to enjoy.

While working, I also had a lot of trouble keeping track of work. I would always save that for the end of the week, and found myself spending hours trying to collect artifacts of what I'd accomplished and thinking about what I actually did. By logging artifacts and work I had done as I finished a session, I drastically lowered the amount of time spent tracking what work I had done. It also made it easier to pick up work where I had left off.

Conclusion

Overall, it was through this capstone experience that I was able to create something I am truly proud of while also being able to learn important technical skills. It was through the development of our project that I was able to experience the full software development lifecycle of designing a product from scratch, creating prototypes, and refining the product through user feedback.

For the future of our game, I hope to implement additional levels for Arrays, introduce additional data structures, and create in-game rewards and cosmetics to help reward players for completing levels. A personal goal of mine is to further develop the UI to fit a theme, making it more unique looking. Because the user will spend most of their time looking and interacting with the menu, I want to really polish it into something the user enjoys using and looking at. Additionally, for future data structures, I want to create more fun ways of interacting with the level. With data structures like linked lists and graphs, I have a lot more freedom with the method of representation.

For each level, we'd also like to include dynamic sizing of assets to give the user a unique experience with each playthrough. Including different sizes for each data structure and having dynamic variables will not only help the user learn through different experiences, it can also help the game feel less stale and more fun to play.
